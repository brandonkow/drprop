## Findings that change the build order

### 1. Membership expiry is not enforced at check-in

**Priority: before a real membership pilot. Reproduced.**

A membership with `status='active'` and `renews_at='2000-01-01'` can obtain a fresh code and be checked in. Both issuance and redemption check the status field without considering the renewal date. There is no expiry job in the reviewed repository. It works only if an operator manually keeps statuses current.

Evidence: [issuance and redemption](https://github.com/brandonkow/drprop/blob/6c03a0fce5d3bcc4f7829fe3cc41b2b7b7192f12/supabase/migrations/202610080001_checkin.sql#L32), [membership schema](https://github.com/brandonkow/drprop/blob/6c03a0fce5d3bcc4f7829fe3cc41b2b7b7192f12/supabase/migrations/202610070001_core.sql#L108).

Build server-enforced membership validity, with an explicit Malaysia-time expiry/grace-period rule, suspension and an audited renewal action. Check validity both when issuing and redeeming a code. If the proposed cap is confirmed, enforce allocation/waitlist transitions atomically instead of relying only on operator SQL.

### 2. Appointment and urgent-service rules need a complete operational model

**Priority: before accepting real bookings. Reproduced plus source inspection.**

- With Monday configured as closed, `dp_publish_slot` accepted a Monday 03:00 Malaysia-time slot. Ordinary appointment publication checks the 90-day horizon and overlap, but not opening days/hours. The staff UI also allows every displayed day.
- An urgent request whose two-hour deadline was already two hours past could still be taken and become `confirmed`. The repository has no overdue state, expiry/escalation worker or notification delivery. This should become an explicit recovery workflow rather than silently preserving a within-two-hours promise.
- Customers see eight days, staff publish across 14 days, and the API permits 90 days. Some offered slots are therefore unavailable in the customer's date picker.
- Customer date grouping/formatting uses the device timezone while the adviser screen uses Malaysia time. A travelling customer can see a different day/time without a timezone label.

Evidence: [slot publication](https://github.com/brandonkow/drprop/blob/6c03a0fce5d3bcc4f7829fe3cc41b2b7b7192f12/supabase/migrations/202610070001_core.sql#L361), [urgent assignment](https://github.com/brandonkow/drprop/blob/6c03a0fce5d3bcc4f7829fe3cc41b2b7b7192f12/supabase/migrations/202610070001_core.sql#L393), [customer date window](https://github.com/brandonkow/drprop/blob/6c03a0fce5d3bcc4f7829fe3cc41b2b7b7192f12/app/src/app/consult/schedule.tsx#L46), [customer date formatting](https://github.com/brandonkow/drprop/blob/6c03a0fce5d3bcc4f7829fe3cc41b2b7b7192f12/app/src/i18n/format.ts).

Build one settings-backed calendar, rescheduling/cancellation/no-show states, urgent capacity/deadline handling and a notification outbox with retry and deduplication. The store's actual hours remain a founder input; the mechanism does not need to wait for them.

### 3. Native behavior needs code corrections as well as phone testing

**Priority: before native distribution. Unit mismatch confirmed from matching SDK source; device behavior remains untested.**

The member-card code treats `DeviceMotion.rotation` as degrees: it subtracts 45 and divides by 35. The matching installed and locked `expo-sensors` 57.0.3 iOS implementation passes Core Motion pitch/roll directly. Pitch is in radians. Inputs of 0, π/4 and π/2 all produce `tilt.y = -1` with the current expression, so the intended front/back response is clamped away. See [card calculation](https://github.com/brandonkow/drprop/blob/6c03a0fce5d3bcc4f7829fe3cc41b2b7b7192f12/app/src/components/member-card.tsx#L80) and [Apple's pitch units](https://developer.apple.com/documentation/coremotion/cmattitude/pitch).

The card component also lacks explicit permission, reduced-motion and foreground/background subscription management. It removes its sensor only on component unmount. The [Expo 57 DeviceMotion guidance](https://docs.expo.dev/versions/v57.0.0/sdk/devicemotion/) requires a user-triggered permission request on mobile web.

Separately, app state does not subscribe to auth-state changes or guard `loadFor` responses with a session generation. A request started before sign-out can later write its captured user back into state. This is a source-level race finding, not a reproduced end-to-end session exploit. Profile-save failures are silently swallowed. Add auth/session lifecycle handling, stale-response protection and visible save failures; test sign-out during refresh, expired sessions and offline/resume behavior.

### 4. The launch and verification gates are weaker than the handoff suggests

**Priority: next engineering sprint. Reproduced and inspected.**

- `app/package.json` uses POSIX environment assignments in both export scripts. Standard Windows npm executes these through `cmd.exe`; the assignment is rejected as an unknown command. Linux CI does not catch this. Replace with a portable Node build wrapper or a compatible environment-setting utility and add Windows coverage.
- `npm run verify:media -w @drprop/reels` checks six films under `brand/renders`, not the 39 files under `reels/delivered`.
- The media checker does not require audio, expected dimensions, fps, duration/frame count, a complete file set, hashes or full decode. A correctly tagged **320×180, 5 fps, 0.4-second MP4 with no audio passed** its `check()` function. This is a validator coverage failure, not a claim that the current 39 reels have those defects.
- Three `market-2026-q2-sample-*` files sit in a folder whose README calls its contents ready to post. Their on-screen warning is helpful, but samples should be segregated from release assets and rejected by a publication manifest.
- Website placeholder blocking applies only when `site.origin` is set. Leaving it null produces a deployable static preview containing placeholder contact/registration details and an invalid WhatsApp target. Use an explicit production command that always validates required fields, and make preview state visible with booking disabled.

Evidence: [export scripts](https://github.com/brandonkow/drprop/blob/6c03a0fce5d3bcc4f7829fe3cc41b2b7b7192f12/app/package.json#L57), [media command](https://github.com/brandonkow/drprop/blob/6c03a0fce5d3bcc4f7829fe3cc41b2b7b7192f12/reels/package.json#L11), [checker](https://github.com/brandonkow/drprop/blob/6c03a0fce5d3bcc4f7829fe3cc41b2b7b7192f12/reels/scripts/deliver.ts#L96), [conditional launch guard](https://github.com/brandonkow/drprop/blob/6c03a0fce5d3bcc4f7829fe3cc41b2b7b7192f12/web/vite.config.ts#L110).

### 5. Dependency findings need current triage

The fresh audit still reports the braces, node-forge and decode-uri-component advisory families. The last one propagates through query-string and Expo Router; it should not simply be grouped with build-only tooling. The audit now offers a newer Expo Router major as one remediation path, while other suggested automatic fixes include large framework downgrades. Do not apply them indiscriminately.

Classify actual runtime/build exposure, select SDK-compatible fixes or narrowly tested mitigations, and add an explicit dependency check with documented exceptions. A passing current CI run does not imply a clean dependency audit: its install log itself contains the 24 affected entries.
